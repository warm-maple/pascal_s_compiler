# 中期汇报讲稿提纲

这份稿子按老师要求控制在 10 分钟左右，建议 4 个人上台。

## 1. 时间分配建议

1. 郝政伟：3 分钟，讲总体进展、架构升级、平台结果
2. 张睿渤：2 分钟，讲词法分析与定位信息
3. 孔力帆：2 分钟，讲语义分析、符号表与类型检查
4. 吴锡华：2 分钟，讲代码生成与 C 映射
5. 郝政伟：1 分钟，讲亮点、加分项和下一步计划

## 2. 组长开场稿

可以直接按下面这段讲：

“我们组本阶段完成了 Pascal-S 到 C 的编译器主体实现，并把整体结构从较早期的解析驱动方式，重构为更清晰的三阶段流水线：语法分析、语义分析、代码生成。除了基础语法和控制流，我们还补全了函数、数组、布尔字面量、错误定位，并扩展支持了 record 结构和多级字段访问。  
在工程上，我们重点做了三件事：第一，把符号表和类型检查从 parser 中拆出来，形成独立的语义分析模块；第二，把错误提示升级成带源码和 caret 的定位形式；第三，自建了一套课程测试集，并最终在平台上做到 95/95 全部通过。  
当前项目已经能稳定通过平台评测，接下来我们会继续完善最终文档、模块说明和展示材料。” 

## 3. 张睿渤发言要点

建议围绕这三点：

1. `lexer.l` 基于 `flex` 完成 token 识别。
2. 注释、关键字、常量、运算符等都在词法阶段分类处理。
3. 本阶段额外做了行列号追踪，为后面的 caret diagnostics 提供定位信息。

推荐一句总结：

“词法分析的目标不只是把字符流切成 token，还要给后续错误提示提供准确的位置基础。”

## 4. 孔力帆发言要点

建议围绕这四点：

1. 新增 `SemanticAnalyzer`，独立做 AST 遍历。
2. `SymbolTable` 负责作用域和标识符管理。
3. `TypeResolver` 负责表达式类型、数组元素类型和 record 字段类型查询。
4. 当前能检查未声明标识符、类型不匹配、参数错误、record 字段不存在等问题。

推荐一句总结：

“语义分析层把 parser 和 codegen 中原本分散的类型规则集中起来，让错误更早暴露，也让代码生成更稳定。”

## 5. 吴锡华发言要点

建议围绕这四点：

1. 代码生成器把 AST 翻译成标准 C 代码。
2. 重点处理了数组下界偏移、函数调用参数、`var` 参数和 record 到 `struct` 的映射。
3. 对调用和声明逻辑做了去重，减少重复代码。
4. 生成结果可以直接给平台后续 C 编译流程使用。

推荐一句总结：

“后端不只是把语法形式翻译过去，而是把 Pascal-S 的语义正确地映射到 C 的执行模型。”

## 7. 答辩高频问题建议回答

### 问：为什么要把语义分析从 parser 里拆出去？

答：
“因为 parser 的职责应该是建 AST，如果同时在里面做符号表插入和类型判断，会导致副作用过多，后续扩展特性时很难维护。拆开之后每一层职责更清晰，也更符合编译器经典流水线设计。”

### 问：record 支持体现在哪里？

答：
“一方面在语法树里新增了 record 相关结构和字段访问节点，另一方面在代码生成阶段把它映射为 C 的 struct，并支持多级字段访问。”

### 问：你们有没有做课程要求之外的扩展？

答：
“有。本阶段比较明确的扩展包括 record 结构支持、多级字段访问、带源码和箭头定位的错误诊断，以及课程自建测试集。这些都不是最初最基础的最低实现，而是为了让编译器结构和展示效果更完整。”

### 问：你们是不是很早就通过了全部测试？

答：
“我们比较早完成了平台全量通过，但课堂展示里我们更关注项目本身的设计和验证过程，所以 PPT 只展示最终结果，不把时间先后作为主要内容。”

### 问：你们怎么验证项目正确性？

答：
“除了平台公开和隐藏测试，我们还自己补了一套课程测试，覆盖成功样例和错误样例；此外还用更严格的 C11 方式检查生成代码，保证生成结果尽量规范。”

### 问：你们当前还有什么不足？

答：
“目前主体功能和平台适配已经完成，但从工程质量角度还可以继续优化，例如进一步拆分较大的 codegen 模块、补充更细的设计文档，以及继续丰富教学型测试样例。”

## 8. 一个重要提醒

答辩时 PPT 里不要放“本次发言安排”或“谁没上台谁上台”这类课堂管理信息。  
这类信息只保留在你们自己的讲稿里即可。

另外，不要主动展开“到底谁写了多少代码”。  
更稳的说法是：

- 按模块负责人介绍
- 强调接口如何协作
- 强调架构、测试和结果
- 把团队内部贡献问题留在组内消化，不带到课堂上

这会更专业，也更安全。
