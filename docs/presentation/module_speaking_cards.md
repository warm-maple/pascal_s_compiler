# 模块发言卡片

这份材料是给上台同学直接使用的，不求面面俱到，但要保证每个人都能在 1 到 2 分钟内把自己的部分讲清楚。

## 1. 郝政伟：总体进展与收尾

### 开场建议

“我们组本阶段完成了 Pascal-S 到 C 的编译器主体实现，并把整体结构从较早期的解析驱动方式，重构为更清晰的三阶段流水线：语法分析、语义分析、代码生成。  
除了基础语法和控制流，我们还补全了函数、数组、布尔字面量、错误定位，并扩展支持了 record 结构和多级字段访问。  
目前平台测试已经达到 95/95 全通过，同时我们还补了课程自建测试集和更严格的生成代码检查。”

### 收尾建议

“从当前阶段来看，项目已经完成了主体功能，并且在结构上比初版更清晰、更适合后续维护。后续我们会继续完善最终报告、模块说明和展示材料，保证最终验收时不仅能通过测试，也能把设计思路讲清楚。”

## 2. 张睿渤：词法分析

### 建议讲稿

“我负责的是词法分析部分，主要文件是 `lexer.l`。这一层的任务是把源程序的字符流切分成 token，比如关键字、标识符、常量、运算符和界符。  
我们使用 `flex` 生成词法分析器，这样就不需要手写状态机，只需要给出匹配规则即可。  
另外，本阶段词法分析不仅负责识别 token，还负责维护行号和列号信息，为后面的错误定位提供基础。也就是说，编译器能在报错时指出源码的具体位置，这部分信息最早就是从词法分析阶段记录下来的。”

### 一句总结

“词法分析解决的是‘这一串字符是什么单词’，并为后续错误提示提供准确的位置基础。”

## 3. 孔力帆：语义分析与符号表

### 建议讲稿

“我负责的是语义分析和符号表部分。语法分析只能保证程序结构合法，但不能保证程序含义正确，比如变量是否声明、类型是否匹配、参数是否正确，这些都要在语义分析阶段判断。  
我们新增了独立的 `SemanticAnalyzer`，在 AST 构建完成之后再进行一次遍历。  
其中 `SymbolTable` 用来管理变量、常量、函数和参数的信息，并通过作用域栈实现查找；`TypeResolver` 用来统一处理表达式类型、数组元素类型和 record 字段类型，避免类型规则在多个模块里重复实现。  
目前这部分已经能检查未声明标识符、赋值类型不匹配、参数错误、引用参数必须是左值，以及 record 字段不存在等问题。”

### 一句总结

“语义分析解决的是‘这棵语法树在含义上是否成立’，而符号表和类型系统是它的核心支撑。”

## 4. 吴锡华：代码生成

### 建议讲稿

“我负责的是代码生成部分，主要目标是把 AST 翻译成等价的 C 代码。  
由于 Pascal-S 和 C 并不是完全一样，所以这里不只是简单拼接字符串，还要做语义映射。  
例如 Pascal 数组可以有任意下界，而 C 数组默认从 0 开始，所以生成时要做下标偏移；`record` 要映射成 C 的 `struct`；`var` 参数要映射成指针参数。  
本阶段我们还对调用参数处理和声明输出做了去重，使代码生成逻辑更集中，减少重复代码，后续更容易维护。”

### 一句总结

“代码生成解决的是‘怎样把 Pascal-S 的语义稳定地翻译成 C 的执行模型’。”
