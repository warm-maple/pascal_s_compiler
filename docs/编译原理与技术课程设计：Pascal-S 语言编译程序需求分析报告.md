# 编译原理与技术课程设计：Pascal-S 语言编译程序需求分析报告

## 1. 引言与目标

### 1.1 项目背景与核心任务
本项目为《编译原理与技术》课程的综合实践环节，任务为**“Pascal-S 语言编译程序的设计与实现”**。本项目的基本要求是：严格按照指导材料给定的 Pascal-S 语言语法规则（包括语法图与文法产生式），参考标准 Pascal 语言的语义规范，遵循软件工程思想，从零开始完整设计并实现一个 Pascal-S 语言的编译程序。

在项目开发周期内，团队需遵循规范的软件工程分阶段开发流程，不仅需要交付最终的系统源代码和可执行程序，还须按阶段输出各设计文档。具体交付物包括：需求分析报告、总体设计报告、详细设计报告、测试报告以及程序使用说明。

### 1.2 系统需求目标
本编译程序的需求目标从工程实践角度细化为以下四点：
1. **编译功能实现**：将词法分析、语法分析、语义分析及代码生成理论落地，系统需能够正确解析合法的 Pascal-S 源程序，并将其转换为等价的目标代码（C 语言或汇编语言）。
2. **需求的可验证性**：本报告所界定出的各类词法、语法、语义及错误处理需求，均须满足“可验证”标准。后续的测试用例需与本报告中的需求点建立一一映射。
3. **模块化与高内聚**：针对编译程序这一复杂的系统软件，需将宏观任务合理拆解为独立的子模块（如词法扫描、语法解析、符号表管理、错误处理等），规范模块间的数据结构与接口约束。
4. **健壮的容错机制**：在实现基本翻译功能的基础上，系统需具备错误检测、精准定位及错误恢复机制，避免遇到单一错误即崩溃，保障编译器的稳健性。

## 2. 源语言特性与编译规范需求

本章节针对被编译语言（Pascal-S）的语法规则、词法约定以及语义结构进行分析，明确编译器需要处理的语言边界与规范。

### 2.1 整体文法与程序结构
根据给定规范，Pascal-S 文法本质上是一个 **LALR(1) 文法**。编译器须能正确解析以下宏观结构：
* **程序头**：以 `program` 关键字引导的程序标识（如 `program example(input, output);`）。
* **全局常量声明（可选）**：以 `const` 关键字引导的常量定义域。
* **全局变量声明（可选）**：以 `var` 关键字引导的变量定义域。
* **子程序定义（可选）**：包括过程（`procedure`）和/或函数（`function`）的声明与实现定义。
* **主程序体/复合语句**：以 `begin ... end` 包裹的主体执行逻辑结构。

### 2.2 嵌套规则与控制流特性
编译器在语法与语义解析阶段，必须严格遵守以下作用域与嵌套限制：
* **子程序嵌套限制**：Pascal-S 语言明确规定，过程和函数的定义**不允许嵌套**。
* **复合语句嵌套**：复合语句（`begin ... end`）**允许进行多层级嵌套**，以支持复杂的控制流逻辑。
* **递归调用**：语言原生支持过程和函数的递归调用，编译器在符号表管理与代码生成时须支持递归上下文的正确维护。

### 2.3 过程、函数及标识符语义规范
* **参数传递机制**：源语言支持两种参数传递方式：**传值调用**（Value-parameter）和**引用调用**（传地址，Var-parameter）。编译器需在目标代码生成时准确区分并实现这两种机制。
* **标识符的语义消歧**：文法中存在 `factor -> id` 的多态性结构。对无参数函数的调用和对简单变量的引用，在语法上没有区别。编译器必须在语义分析阶段依托符号表解决此多义性（例如对赋值语句 `a:=b`）：
  * 若判定 `b` 是常量名，则将 `b` 的值赋予 `a`；
  * 若判定 `b` 是简单变量，则将 `b` 的右值赋予 `a`；
  * 若判定 `b` 是函数，则执行函数调用，并将返回值赋予 `a`。

### 2.4 词法与基础符号约定
编译器词法分析模块需严格遵循以下约定：
* **标识符（id）**：以字母开头的字母数字串，**不区分大小写**。编译器可对最大长度进行合理限制（例如限定前 8 个字符有效）。
* **关键字与保留字**：包括 `program`, `var`, `procedure`, `begin`, `if`, `else` 等。除文件开头的 `program` 和末尾的 `end` 外，关键字前后必须有空格符或换行符分隔。
* **常数（num）**：支持无符号的整型常数与实型常数。
* **注释处理**：代码注释采用 `{......}` 的包围形式。注释可出现在任何单词之后，编译器必须静默过滤注释，不影响后续语法分析。
* **运算符定义**：支持关系运算符（`relop`：`=, <>, <, <=, >, >=`）、加法类运算符（`addop`：`+, -, or`）、乘法类运算符（`mulop`：`*, /, div, mod, and`）及赋值号（`:=`）。

## 3. 系统功能详细需求

本章节按照编译程序的典型执行阶段，对系统功能进行详细定义，作为后续总体设计与测试用例编写的标准。

### 3.1 词法分析功能需求
词法分析器作为基础模块，作为语法分析器调用的独立函数运行，核心需求如下：
1. **单词分类与识别**：系统应能按照正则表达式或有限自动机原理，准确切分源程序，识别关键字、标识符、常数、运算符及界符。
2. **内部编码映射**：为各类单词分配全局唯一的内部类别编码，并以 `<类别编码, 属性值>` 的形式返回给语法分析器。
3. **冗余字符过滤**：自动忽略源程序中的所有空白符（空格、制表符、换行符）以及 `{...}` 包围的注释文本。
4. **位置信息追踪**：在扫描字符流的过程中，实时记录每个单词在源程序中的绝对位置（精确到行号与列号），为错误定位提供数据支持。

### 3.2 语法分析功能需求
语法分析器以词法分析器输出的单词序列为输入，验证程序的结构合法性：
1. **结构解析能力**：能够正确判定输入的记号流是否符合 Pascal-S 语法规则。
2. **分析引擎实现**：系统需选用适当的分析方法。如采用自顶向下的预测分析方法，需对文法消除左递归并提取左因子；如采用自底向上的 LR 分析方法，需构造 LALR(1) 分析表（允许手工编码或借用 YACC 等工具辅助生成）。
3. **语法制导支持**：在识别合法句型的同时，需预留或直接触发语法制导翻译动作，为语义分析和代码生成做准备。

### 3.3 语义分析与符号表管理需求
语义分析阶段的核心是静态类型检查与符号表维护：
1. **符号表内容记录**：动态记录标识符的属性，包括名字、类型、常量值、数组维数及上下界、函数/过程的参数个数及传递方式等。
2. **符号表管理操作**：符号表管理模块必须提供以下四项基本操作：
   * **查找**：按给定的名字查表，验证是否已声明。
   * **插入**：在符号表中建立新的一行记录。
   * **定位**：在创建子程序时，确定一个新作用域的起点。
   * **重定位**：在退出当前过程时，将局部于该过程的所有名字从符号表中“删除”或隐蔽，退出当前作用域。
3. **静态类型检查**：进行严格的语义约束检查，包括但不限于：变量是否未声明即使用、重复声明检查、赋值语句左右部类型相容性检查、数组下标越界（静态可判断部分）、函数调用参数数量与类型匹配等。

### 3.4 代码生成功能需求
1. **目标语言选择**：系统采用 **C 语言** 作为目标语言，生成的 .c 文件可直接用 GCC 编译执行。
2. **结构映射翻译**：由于 Pascal-S 结构和 C 程序结构不完全一致，系统不能简单逐句翻译。需正确处理源程序中的变量作用域映射、控制流转换以及传值/传地址逻辑。
3. **代码可执行性保障**：生成的 C 代码必须能够通过 GCC 编译执行，并保证运行结果与源语言期望的逻辑行为完全一致。

## 4. 错误处理与恢复需求

作为一个达到工程化标准的编译器，遇到非法输入时的容错与反馈能力是系统的重要考核指标。

### 4.1 全阶段错误探测
系统必须具备在各个编译阶段检测并分类错误的能力：
* **词法错误**：如非法字符输入、不符合规范的数字或标识符。
* **语法错误**：如括号不匹配、语句缺少分号、控制流关键字缺失等。
* **语义错误**：如标识符未声明、类型不匹配、实参与形参不符等。

### 4.2 精准错误定位与信息报告
* **坐标输出**：当捕获异常时，系统必须结合词法分析器提供的物理位置信息，精准打印出错误发生的行号和列号。
* **人性化报错提示**：系统应输出清晰的错误类型与潜在的错误原因提示信息，严禁由于遇到错误而直接输出底层异常或引发系统级崩溃。

### 4.3 错误恢复与容错机制
* 系统在探测到错误后，必须具备**错误恢复能力（Error Recovery）**。分析程序应采取合理的恢复策略（如跳过出错的部分，直到遇到同步记号如分号或 `end`），从而调整系统内部状态，继续进行后续的编译扫描。
* 得益于错误恢复机制，系统应力求在单次编译执行中，尽可能多地诊断并暴露源程序中存在的多个非相关错误。

## 5. 测试与评测需求

为验证编译器功能是否完全符合需求，系统必须制定并执行严格的测试计划。

### 5.1 本地测试要求
1. **分阶段测试策略**：测试过程需实行“滚雪球”式迭代。首先完成各个独立模块的单元测试，随后进行整体编译流水线的集成测试。
2. **测试用例设计**：需覆盖白盒测试与黑盒测试。在设计测试计划时，**不仅要设计正确的测试用例（正向验证），还必须专门设计含有各类典型错误的测试用例（逆向验证）**，以验证系统的错误定位与恢复功能。
3. **扩展功能测试**：如团队对语言结构进行了扩充（如增加了 `record` 类型、`while` 循环等），必须提供与之对应的专属测试用例。

### 5.2 在线平台评测要求
系统最终代码必须能够在指定的头歌平台（EduCoder）完成自动化评测，并满足以下硬性指标：
1. **公开测试集（open_set）**：总计 70 个测试用例，系统必须正确通过**不少于 60 个**。
2. **隐藏测试集（hidden_set）**：总计 25 个测试用例，系统必须正确通过**不少于 15 个**。

### 5.3 验收与交付需求
* **测试报告撰写**：交付的详细测试报告中，需按功能模块列出测试用例、预期结果、实际测试结果及其对比分析。
* **实机运行验收**：在期末系统验收答辩环节，系统须进行实机演示。重点演示编译全过程，特别是对“错误测试用例”的精准报错与恢复能力，并展示最终目标代码的正确生成与运行结果。
