# 全员现场四点卡

这份材料只服务一个目标：  
如果老师临场点名提问，每个人至少能围绕下面四个点稳定回答。

固定四点：

1. 我负责的模块是什么
2. 这个模块的输入是什么，输出是什么
3. 这个模块主要解决了什么问题
4. 这部分代码大概在哪

建议每个人先把自己的部分读熟，不必逐字背，但至少要能顺着这四点讲出来。

---

## 1. 郝政伟

### 我负责的模块

整体架构与模块集成。

### 输入 / 输出

- 输入：各模块已经完成的词法、语法、语义和代码生成能力
- 输出：一条完整稳定的编译流水线，也就是从 Pascal-S 源程序到 C 程序的最终联调结果

### 主要解决的问题

- 明确主流程 `词法分析 -> 语法分析/AST -> 语义分析 -> 代码生成`
- 把原来混在 parser 里的语义检查拆成独立阶段
- 统一构建、测试和最终验收材料

### 代码大概在哪

- `src/main.cpp`
- `src/semantic_analyzer.*`
- `src/codegen.*`
- `submission/` 下的验收与答辩材料

### 一句话回答模板

“我主要负责整体架构和模块集成，把词法、语法、语义和代码生成接成一条稳定的编译流水线，并完成最终联调和验收整理。”

---

## 2. 张睿渤

### 我负责的模块

词法分析与定位支持。

### 输入 / 输出

- 输入：Pascal-S 源程序的字符流
- 输出：token 序列，以及每个 token 的行号、列号等位置信息

### 主要解决的问题

- 把源程序切分成关键字、标识符、常量、运算符和界符
- 处理空白符和注释
- 为后续错误定位提供位置信息

### 代码大概在哪

- `src/lexer.l`
- `src/token.h`

### 一句话回答模板

“词法分析负责把字符流识别成 token 流，同时记录行列号，这样后面的 parser 和错误处理模块才能继续工作。”

---

## 3. 周柄名

### 我负责的模块

语法分析与解析状态。

### 输入 / 输出

- 输入：词法分析器输出的 token 流
- 输出：抽象语法树 AST，以及解析过程中需要的上下文状态

### 主要解决的问题

- 按 Pascal-S 文法把 token 归约成程序结构
- 在归约动作里构建 AST 节点
- 用 `ParserState` 集中管理解析期临时状态，减少零散全局变量

### 代码大概在哪

- `src/parser.y`
- `src/parser_state.h`
- `src/parser_state.cpp`
- `src/ast.h`

### 一句话回答模板

“语法分析负责根据文法把 token 流组织成 AST，`ParserState` 则负责保存参数列表、局部声明这些解析期上下文信息。”

---

## 4. 蔡禹煊

### 我负责的模块

AST 与公共数据结构。

### 输入 / 输出

- 输入：语法分析阶段识别出的程序结构
- 输出：统一的 AST 节点体系，以及供后续阶段共享的数据结构

### 主要解决的问题

- 给表达式、语句、声明、程序根节点建立统一表示
- 让语义分析和代码生成都能围绕同一棵树工作
- 用 Visitor 模式支持不同阶段统一遍历

### 代码大概在哪

- `src/ast.h`
- `src/ast.cpp`
- `src/token.h`

### 一句话回答模板

“AST 是整个编译器的中间表示，我这部分主要是把程序结构变成统一的树，方便语义分析和代码生成共享。”

---

## 5. 李良顺

### 我负责的模块

语义分析与符号表。

### 输入 / 输出

- 输入：已经构建好的 AST
- 输出：完成语义检查后的结果，以及一张可供后续代码生成使用的符号表

### 主要解决的问题

- 标识符是否声明
- 作用域是否正确
- 赋值和参数类型是否匹配
- `record` 字段访问是否合法

### 代码大概在哪

- `src/semantic_analyzer.h`
- `src/semantic_analyzer.cpp`
- `src/symbol_table.h`
- `src/symbol_table.cpp`

### 一句话回答模板

“语义分析负责判断 AST 在含义上是否成立，符号表负责管理名字、类型和作用域，两者配合起来完成声明绑定和类型检查。”

---

## 6. 孔力帆

### 我负责的模块

类型系统与错误诊断支持。

### 输入 / 输出

- 输入：表达式节点、标识符类型信息、错误发生的位置数据
- 输出：统一的类型解析结果，以及可读性更好的错误诊断信息

### 主要解决的问题

- 统一判断表达式类型、数组元素类型和 `record` 字段类型
- 避免语义分析和代码生成各写一套类型规则
- 让错误信息能显示源码行和箭头定位

### 代码大概在哪

- `src/type_resolver.h`
- `src/type_resolver.cpp`
- `src/error.h`
- `src/error.cpp`

### 一句话回答模板

“这部分一方面统一做类型解析，另一方面把错误信息整理成带源码和箭头的形式，提升了诊断的清晰度。”

## 7. 吴锡华

- 整理构建方式和程序使用说明

### 代码大概在哪

- `course_tests/`
- `user_tests/`
- `submission/06_user_guide/`
- `submission/05_testcases/`

### 一句话回答模板

“这部分重点不是新增语言功能，而是验证生成代码是否正确，并把测试、运行和使用方式整理成可复现的交付材料。”

## 8. 全员通用兜底

如果老师继续追问，每个人都至少可以再补一句：

### 问：你这部分和上下游模块是什么关系？

答：

“我的模块接收上一阶段的结果，再把处理后的结果交给下一阶段，所以它在整个编译流水线里承担的是中间连接和功能落实的作用。”

### 问：你们项目最有代表性的亮点是什么？

答：

“除了基础 Pascal-S 功能，我们还做了语义分析独立拆分、`record` 扩展、`caret diagnostics` 和自建测试体系，这几项比较能体现完整性。”

### 问：你们怎么证明程序是对的？

答：

“一方面头歌平台已经达到 95 / 95，另一方面我们本地还补了课程自建测试和严格 C11 检查，所以不仅有通过率，也有自建验证支撑。”
